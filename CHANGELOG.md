## 3.3.0 — 2026-11-25

### `--socks`: SOCKS proxy / tunnel detection

A SOCKS proxy relays a client's traffic to a destination the client names in the handshake — a tunnel that moves traffic past egress controls, hides the real destination behind the proxy, and is the transport under many C2 implants. `--socks` reads the SOCKS4/4a/5 handshake off the wire and reports it in the same layout as `--vpn`.

- **Structure, not port.** Detection reads the actual greeting / request / reply bytes, so it finds a proxy on 1080, on 9901, or on an ephemeral port alike. A conversation is reported only once a handshake is answered in both directions (greeting → method selection, or request → reply), which kept it to **zero false positives across 138 non-SOCKS captures** while flagging every SOCKS capture in the corpus.
- **What it surfaces:** the proxy and its clients (roles inferred from the handshake), the version (SOCKS4/4a/5), the command (CONNECT / BIND / UDP ASSOCIATE), the **tunnelled target** `host:port` (the destination egress logs never see), the negotiated authentication, the reply status, offered auth methods, and artifact correlations.
- **Hunt reads:** `HIGH` for a **reverse / server-initiated proxy** (the proxy-server role dials out first — the shape of a reverse-SOCKS implant; T1090.001); `MEDIUM` for **cleartext username/password auth** (surfaced like `--creds`, masked under `--redact`; T1090) and for a **tunnel to a sensitive service port** (RDP/SMB/SSH/DB/… — a pivot; T1090); `LOW` for failed-auth attempts, `No acceptable methods`, UDP ASSOCIATE relays, legacy SOCKS4/4a, non-standard proxy ports, and many-clients-to-few-proxies fan-out.
- Feeds the consolidated `--threats` output and participates in `-summarize` roll-ups like every other analyzer.



### `--baseline-diff` reads like an incident report

The drift report listed every deviation; an analyst still had to assemble them into what happened. It now does that, the way `--compromised` reports hosts:

- **Incidents** correlate the deviations per actor with fixed rules: a rogue OT master (with the register values it changed on its targets as the impact), new control activity from a known master, adversary-in-the-middle attributed to the IP that owns the intruding MAC, remote access to an OT asset, process values changed with no writer seen, OT communication lost. Each shows when it ran (first sighting to last activity), its ATT&CK for ICS techniques, the evidence, and the pcapper commands to run next.
- **The headline names the lead incident**, e.g. `HIGH  Rogue OT master 172.27.224.50 writing to 172.27.224.250`.
- **Every deviation carries its first sighting and, where it is the behaviour, its technique** (T0848 Rogue Master, T0855 Unauthorized Command Message, T0836 Modify Parameter, T0830 Adversary-in-the-Middle, T0886 Remote Services, T0831/T0832 Manipulation of Control/View, T0856, T0814, T0806); a **Timeline** orders them.
- **Background chatter** -- broadcast, multicast, link-local and unspecified addresses coming and going -- is counted but kept out of the findings and evidence tables (`-v` shows it). On the Coimbra Modbus captures that was 10 of 16 deviations (ARP man-in-the-middle) and 20 of 26 (Modbus flood).
- A rate 10x the baseline on an OT conversation is reported as `OT traffic flood` (T0814); write/control rates 10x as T0806.
- Baselines now record when each pair command, IP-MAC binding and register extreme was first (and last) seen; `OtCommandSummary.pair_command_times`, `TrafficProfile.ip_mac_times`.

On the Coimbra captures the incidents span 5m 00s (Modbus flood) and 5m 02s (ARP man-in-the-middle): the datasets' documented 5-minute attack windows.

## 3.1.0 — 2026-11-25

### Baselines: `--baseline` and `--baseline-diff`

`--baseline` records what a network normally does; `--baseline-diff` reports what deviates from it, as findings with a severity, in the drift report's usual layout (findings first, then the evidence tables).

- **The profile:** every conversation as client -> server on its service port, classed OT, IoT, IT or other, with volume and request cadence (median interval and jitter); the commands each pair exchanges, reads and writes, from every analyzer `--ot-commands` runs; layer-2 industrial streams (GOOSE, SV, PROFINET RT, EtherCAT, PTP, LLDP); the MAC addresses each IP sent from. Hosts, services and OT command totals as before.
- **The deviations** are fixed rules with named thresholds in `pcapper/baseline.py`: a new OT pair, a new writer to an OT device, remote-access/file-transfer protocols on an OT host, an IP answering from a different MAC, a polling cadence or rate change, an OT conversation gone silent, a new L2 stream, new hosts and services. The full table is in [docs/reference.md](docs/reference.md#baselines).
- **File names follow the capture:** `X.pcap` -> `X.baseline.json` next to it. With `-summarize`, one merged baseline named after the captures' common prefix (`Site-1.pcap`, `Site-2.pcap` -> `Site.baseline.json`). `--baseline PATH` names the file or a directory.
- **The reference can be a capture:** `--baseline-diff known-good.pcap` profiles it and compares, with no file in between.
- **On their own, `--baseline` and `--baseline-diff` print only their report.** `--baseline-save` used to switch on `--services` and `--ot-commands` and print both; the analyses now run silently and are memoized, so asking for them as well costs nothing. `--baseline-save PATH` and `--baseline-compare REF` remain as aliases. Their files (schema 1) still load and compare: the sections they lack are noted, never reported as drift.
- **Modbus register values:** the range each register held (from read responses paired with their requests, and from written values; `ModbusAnalysis.register_ranges`). A register constant in the baseline that now reads differently is HIGH; a value beyond its baseline range is MEDIUM. On the public Coimbra Modbus testbed captures, the Modbus query flood drove the PLC's holding register 6 to 0 where the clean hour held 30..31.
- **`--ot-commands`** records every command per direction of communication (`OtCommandSummary.pair_commands`), in full and fast mode.

Checked against the public [Coimbra ICS_PCAPS](https://github.com/tjcruz-dei/ICS_PCAPS) Modbus/TCP testbed captures: a clean hour as the baseline, the ARP man-in-the-middle hour (the HMI's IP sent from the attacker's MAC, naming the attacker's own IP) and the Modbus query flood hour (a new pair and writer, the register above), with the legitimate HMI polling and writer unflagged in both.

### Faster host inventory

- **Analyses called positionally and by keyword share one memo entry.** `analyze_hostname(path, None)` (the host inventory) and `analyze_hostname(path, target_ip=None)` (the IP analysis) were two cache entries, so `--hosts`, `--hostdetails` and baselines computed host names twice. Positional arguments are now keyed by the parameter they fill.
- **OS fingerprinting reads lightweight records.** It dissected every packet to find TCP SYNs; it now drops non-SYN records, and SYNs from a host already sampled 250 times, from their header bytes, and dissects only the SYNs it samples. Results are identical (pinned by a test against dissected packets). On a 264,000-packet Modbus flood capture the fingerprint pass went from ~23 s to 0.7 s and the host inventory from 93 s to 64 s.

### Fixed

- **CODESYS was labelled "ODESYS"** in the service names, the OT command keys and the OT-presence aliases. The alias mismatch also meant CODESYS traffic never counted as present, so CODESYS findings were dropped from the merged OT view.
- **`--ips`: a host addressing itself was counted twice.** A packet whose source and destination are the same IP counted in both its sent and received bytes, so the endpoint table's TOTAL doubled and "Traffic concentration on a single host" read 200%. Self-addressed bytes now count once (`IpEndpoint.bytes_self`, `bytes_total`).
- **`-summarize`: the merged concentration finding is computed on the merged traffic.** Each capture's own "X accounts for 100% of IP bytes" was carried into the rollup, contradicting the merged endpoint table. It is now recomputed from the merged endpoints.
- **Tests that assumed POSIX now pass on Windows:** the explicit `--jobs` assertion allows for no `fork()`, the loopback fixture uses the IPv6 family scapy binds on the platform (Windows: 24, not `AF_INET6` 23), and the stand-in tshark/Suricata run through a `.cmd` launcher where a shebang script cannot execute.
- **`-summarize`: merged finding details no longer add up IP addresses and percentages.** Merging "same finding, different numbers" summed every digit run, so three captures turned `192.168.121.2 … 200.0%` into `394.418.283.109 … 600.0%`. Only standalone counts are summed now; any other difference lists the variants.

## 3.0.2 — 2026-11-24

### Scan-heavy captures: `--creds` and the analyses it starts dissect only what they read

`pcapper maccdc2010_00000_20100310205651.pcap --creds -v` (10M packets, 925 MB) took 38.7 minutes. 92% of that capture's packets are TCP segments without a payload (scan traffic), and every one was dissected with scapy (about 120 µs each on this machine) by analyses that drop it on the next line: creds, the HTTP analysis it calls for request URLs, telnet, and -- under HTTP -- the file, NFS and AIM analyses. The machine's memory was never the limit.

- **creds, HTTP, telnet, NFS and AIM read lightweight records** (as the OT analyses do). Ports, endpoints and a `Raw` payload come from the record's bytes. A record each analysis would drop is dropped without scapy: no TCP/UDP layer, an empty segment, off its ports, or a payload that does not open like its protocol. Every other record is dissected and takes the unchanged path. creds reads the payload and the Ethernet padding behind it, as `bytes(pkt[Raw])` gives them; telnet checks its option bytes on that longer view, so it keeps any segment the padding-stripped payload could start with.
- **creds no longer starts the file analysis.** It calls HTTP only for request URLs, and that call now skips HTTP's file discovery (`analyze_http(..., discover_files=False)`). In a profile of creds over 250,000 packets, file discovery took 31 of 54 s.
- **creds skips payloads that are NUL bytes only**, the padding behind 6.2M of the capture's 10M packets. Scanned, they give no hit, no error and no SMTP AUTH LOGIN state change. This was checked over every port pair the scan tells apart (117 ports, TCP and UDP, 1–64 bytes, 1.75M payloads) and with padding at every position of an AUTH LOGIN exchange.
- **A run whose analyses all read lightweight records streams a scan-heavy capture from disk** instead of loading every packet with scapy first, even when it fits in memory. On a 250,000-packet `--creds` run that load took about 70% of the time. (Which captures count as scan-heavy: see the next section.)
- **Automatic `--jobs` spreads plans of two analyses or more** (was four). In one process, analyses share one interpreter lock. `--creds` of 1M packets: 38 s in one process, 24.5 s in three; of 250,000, 6.7 s and 5.8 s.

| `--creds -v`, maccdc2010 | Before | Now |
|---|---|---|
| 250,000 packets, in memory (default) | 47.6 s | 5.8 s |
| 250,000 packets, from disk | 40.2 s | 5.7 s |
| 1M packets (from disk) | 191 s | 24.5 s |
| 10M packets, full capture | 2,321 s (38.7 min) | 384 s (6.4 min) |

With `-v`, the large-capture notice no longer reads as a forecast of the run for such a plan: "Dissecting it once would take ~17 min on this machine (~118 µs/packet); this run's analyses dissect only the packets they look at." Scapy's dissection warnings (`Unknown cipher suite … from ClientMasterKey`) now print in a different order, once per process that dissects the packet. `--creds -v` no longer prints the cryptography deprecation warnings that the file analysis's certificate parsing raised.

Reports are byte-identical to before. Checked over 113 captures (IT, OT, malware, VLAN, IPv6, Linux cooked, pcapng) × `--creds`, `--http`, `--telnet`, `--nfs`, `--aim`, `--files`, `--creds --http`, `--dns --http` and `--threats`, in memory and from disk (2,034 comparisons); 168 OT captures from 68 datasets × five OT flag combinations that now stream instead of loading (840); and the full capture. `tests/test_lite_it_paths.py` pins each analysis from disk against the same analysis over scapy packets, on edge-case frames (non-zero padding, VLAN, IPv6, IP options, telnet options on another port, NFS over TCP and UDP, AIM on 443, SNMP, ICMP with a payload, STP over LLC/SNAP). Deliberately breaking the creds or telnet fast path fails it.

### `--threats` and `--overview`: every analysis reads lightweight records

The same treatment for every analysis `--threats` and `--overview` start that still had scapy dissect every packet: 43 of them -- the capture summary and protocol hierarchy, scans, TCP and UDP statistics, IPs, hosts and services, beaconing, exfiltration, routing, ICMP, ARP, DNS, DHCP, NetBIOS, LDAP, Kerberos, NTLM, SNMP, syslog, SMB, RDP, WinRM, WMI, PowerShell, DCE/RPC, VNC, remote access, TLS, certificates, QUIC, encrypted DNS, VPN, SSH, FTP, e-mail, malware, obfuscation, carving, CTF, VoIP, host names and the threats loop itself. Neither run dissects every packet of a capture any more.

- **Each skips a packet only where its original code provably does nothing with it** (no TCP/UDP layer, off its ports, no payload, a payload without the bytes it looks for -- checked on the same bytes, Ethernet padding included where the original reads it), and dissects every other packet into its unchanged scapy code. The analyses that count every packet (summary, protocol hierarchy, scans, TCP/UDP, IPs, beaconing, exfiltration, services, threats, host names) read the fields they count -- addresses, MACs, ports, TCP flags and sequence numbers, IP lengths, TTLs, VLAN ids, layer names -- from the header bytes for plain Ethernet/IP/TCP/UDP packets, and leave the rest to scapy. Where a skip rests on a claim about payloads (a NUL-only payload holds no host name, no credential), the claim was checked exhaustively over every port the analysis tells apart.
- **A TCP segment scapy cannot parse is left to scapy.** scapy keeps a segment whose TCP-AO option (kind 29) has a one-byte value as Raw -- the packet has no TCP layer -- and the lightweight parser now says so (it answered as for a TCP header before, in every lightweight analysis).
- **Streamed or loaded, by what the capture holds.** When every analysis reads lightweight records, a capture of 8 MiB or more whose first 256 KiB of records are 60% or more payload-less packets (a scan) is streamed even when it fits in memory; a capture whose packets mostly carry data is loaded, as before -- streaming it dissected its packets once per `--jobs` worker, and in one process handed every record to a hundred analyses (a 3,400-packet Dridex capture's `--overview`: 27.3 s streamed, 8.6 s loaded). `PCAPPER_LITE_STREAM=1` always streams such a run, `=0` never does.

| maccdc2010, default (automatic `--jobs`) | Before | Now |
|---|---|---|
| 250,000 packets, `--overview` | 63.1 s | 17.2 s |
| 250,000 packets, `--threats` | 59.8 s | 14.6 s |
| 1M packets, `--overview` | 265.2 s | 73.4 s |
| 1M packets, `--threats` | 258.1 s | 65.0 s |
| 10M packets (full capture), `--overview` | 69.6 min | 19.0 min |

Captures whose packets mostly carry data run as before: NM_2015-08-23 (20k packets) `--overview` 10.5 s / 10.5 s, `--threats` 9.4 s / 9.5 s; wannacry-20170516 `--overview` 7.3 s / 7.1 s; a Dridex infection capture `--overview` 8.7 s / 8.7 s. An OT capture of 379k Modbus packets (cic-modbus-2023, 80% of its first records payload-less) is streamed: `--overview` about 12 minutes before, 10.5 now.

Reports are byte-identical to before. Checked old tree against new, byte for byte: 41 flag sets (every analysis changed, `-v`) over 113 IT/OT/malware captures, plus captures picked for each protocol from a port index of 1,600 corpus captures and the 250,000-packet scan, in memory and from disk -- 10,388 comparisons; `--threats -v` and `--overview -v` over the same captures and OT flag combinations over 56 OT captures, both modes -- 792; every flag again in memory under the final stream-or-load rule -- 4,859; and `--overview` of the full capture. Each analysis has a test comparing it from disk with the same analysis over scapy packets on edge-case frames (`tests/test_lite_*.py`), and the tests were checked to fail when a skip is deliberately broken.

## 3.0.1 — 2026-11-23

### `--jobs` uses the machine

An `--overview` of a 10M-packet capture (maccdc2010, 883 MB, from disk) took 80 minutes on a 72-CPU machine with 4 of its CPUs busy: the main process read the capture, fed copies to 3 workers and ran the 16 heaviest analyses itself (hostname, the capture summary, threats, IPs, malware, TLS ...), because they needed other analyses' results; the workers ran at its pace. On a 250,000-packet slice `--jobs 8` and `--jobs 16` gained nothing over the default.

- **Workers take every analysis, dependent ones included.** Each worker computes a share of the plan side by side (in a shared pass from disk, on threads in memory). An analysis needing a result another worker computes runs its own packet loop meanwhile, then waits for the result, which its worker sends up as soon as it is done and the main process passes on to the workers waiting for it. A result that cannot be sent, or a worker that fails, leaves the analysis to be computed where it is needed, as before. From disk only the analyses reporting the capture's hashes stay in the main process, whose read computes them. In memory a dependent analysis no longer waits to be started until everything it needs is done (that chain -- hostname, IPs, malware, threats -- was the run's length).
- **No deadlock from waiting workers.** A worker whose analyses all wait for others before reading still drains its copy of the capture (one lightweight reader takes the first round), so the main process's read -- and every other worker -- never stalls on it.
- **Balanced by measured cost.** Workers are grouped by each analysis's measured cost (hostname ~7x a typical analysis) instead of two weights; from disk, analyses that read lightweight records are grouped apart, so their workers never dissect the capture with scapy. The plan's dry run now notes what each analysis reads.
- **Automatic count: one per usable CPU, at most 16** (was 8); from disk no longer cut to the 3 workers that kept pace with the main process.
- `--overview`, maccdc2010 slice of 250,000 packets: from disk 212 s → 68 s; in memory 132 s → 62 s (of which 32 s is loading the packets with scapy). Full capture (10M packets, from disk): 80 min → 70.5 min only -- 16 workers busy throughout, each spending about as long as one of the 4 processes did before: on a capture this size a worker's time is dominated by what does not shrink with fewer analyses (dissecting every packet once, and costs that grow faster than the packet count), not by its share of the analyses.

### Faster analysis

- **hostname**: MAC normalisation and address parsing are cached (a capture has few distinct ones), and the CDP check no longer rebuilds every frame without a payload: a dissected layer whose header cannot open the SNAP header cannot hold CDP. 7.1 s → 4.7 s on 50,000 packets.
- **capture summary** (`analyze_pcap`): looking for interface attributes no longer makes scapy search every layer's fields nine times per packet when no layer has such a field (a Linux cooked v2 capture's `ifindex` still answers); `pkt[TCP]` is looked up once. 3.7 s → 2.4 s on 50,000 packets.
- **Packets dissected from disk keep their layer lookups** for the analyses sharing them, as packets held in memory already did.
- **A run no longer pauses at exit**: the interpreter's last garbage collection walked every object still alive -- up to 16 s with 250,000 packets in memory. They are frozen first.

Every change was checked against 3.0.0: reports byte-identical on 32 captures (OT, malware, IT, attack sets; in memory and from disk; `--jobs 4` and automatic -- 128 comparisons), hostname and capture-summary results identical on 22 captures, and the new tests (`tests/test_jobs_groups.py`) pin the group workers, result frames, cost balancing and each fast path.

## 3.0.0 — 2026-11-20

### Reports redesigned

Every report was rewritten, one analyzer at a time (OT first, then IT, then the cross-analyzer reports), to be short by default and complete with `-v`. Nothing was dropped: each new `-v` report was checked token by token against the old `-v` report on real captures, and every value the old report printed is still printed (or was a label, a rounding of the same value, or one of the analysis-only sections below).

- **One house style.** A report is a title, a headline (a severity badge — `CRITICAL`/`HIGH`/`MEDIUM`/`LOW`/`INFO`, the CVSS/Sigma vocabulary — with what it means and the capture scope), then sections; the default view ends with what `-v` adds. Tables are aligned and borderless and say how many rows `-v` adds; times are ISO-8601 UTC (to the microsecond with `-v`); a protocol that is absent is one line; long text is cut at a word boundary.
- **Findings first.** Detections are grouped by type with their flow, time, count and ATT&CK technique; the evidence behind each is listed with `-v`.
- **Analysis-only sections are no longer printed:** the "Deterministic … Security Checks" blocks and the scored "Analyst Verdict" (now a `-v` "Assessment" with its score and reasons). Their code is kept for a future `--analyze`.
- **Threat Hunt / Forensics / CTF / OT highlights, Immediate Leads and Auto-Run Deep Dives appear in `--overview` only**, and there each line appears once. Before, the same line was repeated across the highlight blocks, the leads, the focus list and the deep-dive table; a lead for critical/high detections was tagged MEDIUM; the deep-dive table cut words in half.
- **`--scan`, `--overview` and `--threats` are concise by default like every other report** (they used to always print everything).
- **Repeats are folded.** `--timeline` shows each distinct event once at its first sighting with ×N and its last time (422 events of a Modbus capture become 8 rows; `-v` lists every event in order); `--threats` and `--hostdetails` list a detection two analyzers raised ("SMBv1 detected" from Files and SMB) once with both sources; `--hostdetails` folds identical authentication events.
- **New in the reports:** `--ctf` lists each distinct flag with the packet, flow and decode chain that carried it, and HTTP credentials apart from flags; remote-access reports decode PowerShell `-EncodedCommand` payloads; the capture summary shows how many packets the snaplen cut short; `-summarize` rollups for analyzers without their own merge aggregate every capture's detections ("in 2 of 3 captures"); several reports that never printed their detections or errors (NTP, QUIC, HTTP/2, encrypted DNS, decode, decrypt) now do.
- `--split` windows, the packet view and the self-check use the same title style; `-summarize` rollups are separated by one blank line instead of two.

### Progress display

- **The run header shows the quote of the day** under the name and version (`PCAPPER_QUOTE` / `PCAPPER_QUOTE_SEED` choose it, as for the banner).
- **One progress bar per capture, and nothing else, unless `-v`.** A run used to interleave a `Processing name N%` line per read pass, a spinner per analysis (`Threats name - 6.7s`), scapy's per-record warnings (`WARNING: Unknown cipher suite … from ClientMasterKey`, glued onto the status text) and Python warnings (cryptography deprecations). Now stderr shows `[2/5] name.pcap ━━━━━━━━━━──────── 62%  0:41` — moved by read passes and by every finished analysis, each weighted by its cost (the shared pass's 0.1 s dry run counts what a step will compute; payload-scanning IT analyses weigh six times a port-filtered OT one, a packet-loading read forty) — and takes it away when the capture is done.
- **`-v` shows the detail instead**: each read pass's percentage, each analysis's spinner and start/finish timing, scapy's and Python's warnings, and the large-capture and auto decode-as notices. Every one is on its own line: a warning, notice or report line takes the status line off the screen first, and the bar comes back below report output that is printed while it runs.
- Errors still print without `-v`; `--no-status` (and stderr that is not a terminal) draws no bar; an explicit `-W` / `PYTHONWARNINGS` still decides which Python warnings show.
- A shared-pass dry run no longer caches "no auto decode-as detections" for a capture: the empty packet view it runs over would have turned decode-as off for the real run.

### Faster analysis

`--threats` on wannacry-20170515 (49k packets): 153 s -> about 100 s, with every report byte-identical (every analyzer flag on seven captures, in memory and from disk, compared against the previous code).

- **String extraction runs in C.** The printable-ASCII and UTF-16LE string scans every payload analyzer uses looped in Python byte by byte (75 s of a profiled --threats); they are one regex scan now (the wide-string scan masks with one big-integer AND), checked against the old loops on 3,000 random buffers. The WMI, RPC, PowerShell and LDAP copies use the shared scan, each keeping its own alignment rule.
- **A TLS record's bytes are built once per run**, not once per analyzer: the keep-once rule the shared pass used now also serves runs that hold the capture in memory.
- **Layer lookups are kept per packet**: a packet held in memory answers `getlayer` / `haslayer` from its own table after the first time (6M lookups, each walking the layer chain, in that run).
- **Six malware-tooling and eight PowerShell patterns are screened with one search** per text; only a text the combined pattern matches is checked pattern by pattern.

### Read once

Whatever the flags, a run reads its capture once and computes every analysis from that read -- with `--jobs` processes and Suricata included. Bytes read from NM_2015-08-23 (20k packets, 13 MB) per run by every process, in file sizes (strace):

| Run | In memory, before → now | From disk, before → now |
|---|---|---|
| `--http` | 2.53 → 1.00 | 4.57 → 1.00 |
| `--http --dns` | 1.50 → 1.00 | 5.61 → 1.00 |
| `--tls` | 2.53 → 1.00 | 6.65 → 1.00 |
| `--files` | 1.50 → 1.00 | 3.53 → 1.00 |
| `--http --dns --tls --files` | 1.50 → 1.00 | 7.69 → 1.00 |
| `--overview` | 2.50 → 1.00 | 9.06 → 1.00 |
| `--threats` | 1.50 → 1.00 | 7.78 → 1.00 |
| `--timeline -ip` | 2.51 → 1.00 | 4.71 → 1.00 |
| `--hostdetails -ip` | 2.51 → 1.00 | 8.67 → 1.00 |

Header checks add 4 KiB at most (0.05 of a 86 KB capture, nothing visible here). With `--jobs`, from disk too (see `--jobs` below); with `--suricata`, Suricata included.

A pcapng was read more often still -- wannacry-20170516 (5.8 MB), in memory / from disk: no flags 5.07 / 4.01, `--http` 4.10 / 5.21, `--http --dns` 3.03 / 6.25, `--overview` 4.03 / 15.86 -- and now reads once too (1.00 every one, see "pcapng details from the same read"). So do split captures (a 3-part NM_2015-08-23: the summary and `--overview` 2.00, `--suricata` 3.00, `--http --dns --tls --jobs 2` from disk 3.00 -> 1.00) and gzip-compressed ones.

- **One plan per run.** A dry run (~0.1 s) finds every analysis the requested steps start, including the ones a step runs inside itself (the file analysis behind `--http`, QUIC and certificates behind `--tls`, host names behind `--ips`). A run that starts more than one is loaded into memory when the capture fits -- `--http`, `--tls` or `--timeline` alone read the file once per analysis -- else every analysis of every step is computed in one shared pass from disk, instead of a plan per fan-out step.
- **Analyses that combine others read first.** `--threats`, the domain analysis, `--timeline` and the hosts' OS fingerprints read their own packets after the dozens of analyses they combine, so each started another read -- and dissected every packet again -- after the shared one: three to four reads for `--threats`, `--overview`, `--mitre` and `--compromised` from disk. They now read first and combine afterwards, and the file analysis's two stream passes run side by side. A test pins every planned step combination at one read and fails when a step asks for an analysis its plan did not foresee.
- **Hashes on the way.** The SHA-256/SHA-1 the summary, `--overview` and case metadata report are computed from the read that loads or streams the capture instead of a read of their own (and a plan's dry run no longer reads the file to hash it).
- **The file analysis uses the packets in memory**: its dpkt pass read the file again for every nested call (`--timeline`, `--hostdetails`, `--overview`) even with the capture loaded. In a `--split` window that read was the whole capture, so every window listed the whole capture's file transfers, numbered by packets of the whole file: window 2 of wannacry-20170515 (`--split 2 --timeline -ip 10.10.110.131`) reported 29 malicious-looking file events that all belong to window 1. A window now sees its own transfers.
- **Headers once.** Format sniffing, the datalink check and the gzip test read a capture's first 64 KiB once per file version: 379 file opens -> 13 for `--overview` from disk. The datalink check and the scapy reader's format check read through Python's default 128 KiB read-ahead -- all of a small capture -- for a few header bytes; they now read 4 KiB at most, or nothing (the cached first bytes).
- **Estimates only when they decide something.** The sampled packet count (five 1 MiB samples) is taken for the memory budget only when the file's size cannot decide -- every record takes 16 bytes or more -- and for the large-capture note only when `-v` shows it; the automatic `--jobs` count comes from the capture's head the run reads first, kept and replayed. (Smaller samples were tried and dropped: on seven captures their estimates were off by up to 69%, against up to 47% for 1 MiB.)
- **The decode-as check costs no read of its own.** From disk it reads up to the first 50,000 packets before the analyses run (what it finds decides what the OT analyzers see); those records are now kept, up to `PCAPPER_PRIME_MAX_BYTES` (64 MiB), and the read that follows replays them and carries on from where the check stopped -- for a capture of fewer packets, the whole read. If a scapy layer module binds itself in between (scapy's Modbus on 502 once `--modbus` runs), the kept records forget what they worked out and dissect like records read then.
- **Baselines, correlation and `--control-loop` join the plan.** `--baseline-save`, `--baseline-compare` and `--correlate` took their host inventory before the steps, outside the plan, and `--control-loop` combined the Modbus and DNP3 analyses without the plan knowing them, so each of those analyses read the capture on its own. NM_2015-08-23: `--baseline-save` 2.51 -> 1.00 file sizes in memory, 19.81 -> 1.00 from disk (`--http --baseline-compare` 20.85 -> 1.00, `--http --correlate` 19.12 -> 1.00); `--control-loop` 3.42 -> 1.00. Every one of the 123 analyzer flags on its own now reads the capture once from disk, on a pcap and on a pcapng.
- **`--ioc`, `--streams`, `--carve` and `--packet N` join the plan**, and `--mitre --ioc-file` no longer computes outside it (an analysis given a file path could not be memoised): from disk they share the run's read instead of one each; the IOC analysis reads its packets before the file analysis it checks hashes against.
- **pcapng details from the same read.** A pcapng's interface and section details (interface names, link types, drop counts, the capturing hardware, OS and application the summary shows) came from a walk of the whole file of their own -- before the summary's own loop, again after every load into memory, in the plan's dry run and in each in-memory `--jobs` worker. The run's read now collects them as its bytes go by, with the very parser the walk used (checked against it on 60 pcapng captures, fed in chunks of any size, whole and cut short), the summary takes them after its loop, a dry run reads nothing, and a capture walked once (`--pcapmeta` alone) is not walked again. A compressed pcapng is still walked separately.
- **Split captures read once.** A joined split capture's SHA-256/SHA-1 came from a read of its parts of their own; Suricata's scan of each part read the part, and read it again to hash it (a hash the joined capture's then replaced); from disk the `--jobs` workers each read every part. The hashes now carry on from part to part through the run's read (from a copy of their state at each part boundary, so a part read only in part leaves them as they were; equal to `cat part000 part001 ... | sha256sum`). Each part's Suricata run, and each part's tshark listing for `--decrypt`, is fed a copy of the run's read of that part, started as the read nears the part (never more than about three running at a time, whatever the number of parts). Workers are copied every part through their pipe, each part framed by its size -- or, when they inherit the decode-as head, replay it and are copied the rest from where it stopped. 3-part NM_2015-08-23: summary and `--overview` 2.00 -> 1.00, `--suricata` 3.00 -> 1.00, `--decrypt` 3.64 -> 1.64, `--http --dns --tls --jobs 2` from disk 3.00 -> 1.00; asprox_24hr in four parts, `--http --dns --modbus --jobs 3` from disk 1.01 (1.31 while the workers were copied the head again). Reports byte-identical to before.
- **gzip-compressed captures read once.** pcapper now inflates a compressed capture itself, under its readers: the copies that want the capture inflated (Suricata, tshark's listing) are fed it from the run's read, and a compressed pcapng's details come from that read too (wannacry-20170516 compressed: 2.05-2.10 -> 1.05-1.10, the rest being format sniffs of the compressed file; `--decrypt --http` 3 -> 2).
- **Filters read once too.** With `--bpf`, tcpdump read the capture by name while the analyses read it again for what tcpdump cannot hand on -- a pcapng's details -- and the analyses nested in others (the NFS check inside the file analysis) were never given the filtered packets, so they read the whole capture, unfiltered. tcpdump now filters a copy of pcapper's own read, down its standard input (with scapy's options; macOS's tcpdump reads no standard input and keeps reading the file), and every analysis of a filtered run sees the filtered packets. NM_2015-08-23 `--bpf tcp --http --dns` 2.55 -> 1.00 file sizes, the same with `--time-start`/`--time-end` 2.56 -> 1.00, wannacry-20170515 (pcapng) 1.00; reports identical, less tcpdump's "reading from file" line on stderr. A gzip-compressed capture is filtered too now: tcpdump reads no gzip, and the run fell back to the unfiltered capture.
- **`--files -hash`, `-extract`, `-view` and `--case-dir` join the plan.** The file analysis with any of them was left out of the plan (bare `-hash` even planned a different call than the step made), so from disk it read the capture again in its step: `--files -hash` 3.53 -> 1.00 file sizes from disk. Over a dry run's empty view the extraction extracts nothing, and the step then extracts nothing twice.
- **`--split` hashes on its index walk.** The walk that finds the windows' record boundaries reads every byte; it now hashes them (and collects a pcapng's details) instead of a read of its own for the windows' reports, and each window's time span comes from the window's own read instead of a second one. asprox_24hr `--split 4` 4.18 -> 2.21 file sizes, `--split 4 --http --dns` 10.25 -> 2.21 -- the index walk and the windows' reads: windows of equal packet counts need the count before any window starts. A reader that seeks over records (the walk) keeps hashing across a skip of up to 4 MiB, reading it.
- **A gzip capture's header checks read only its start**: 64 bytes, or a pcapng's first blocks, inflated from 4 KiB reads, where the gzip module read 128 KiB of the compressed file for each (wannacry-20170516 compressed: 1.05-1.10 -> 1.00-1.01 file sizes).
- **A copy that waits is fed first.** With Suricata or `--decrypt`'s listing waiting on the run's read, the run reads the capture before the steps even for a single analysis: a step that came first (`--suricata --modbus`) used to read the capture for its copy -- dropping the decode-as head -- and leave the analysis to read it again. And a forked `--jobs` worker, which inherits the parent's read with the copies on it, used to finish those copies when it closed that read -- reading the rest of the capture in the worker. A read a process inherits now leaves its copies, hashes and pcapng details to the process that opened it. asprox_24hr from disk: `--suricata --modbus` 3.41 -> 1.00 file sizes, `--suricata --http` 5.45 -> 1.01.
- **Suricata can read a copy of the run's read** (`PCAPPER_SURICATA_FEED=1`): started on a FIFO before the run reads the capture, it is fed every byte of that read (or of one made for it), and the hash comes from the same read -- NM_2015-08-23 `--suricata --http` 6.57 -> 1.00 file sizes from disk. Off by default: Suricata 6's results depend on the pace it is fed at, and a run whose own analyses read slower than Suricata reads a file costs it alerts (asprox_24hr: 4,698 alerts from the file or a full-speed feed, 4,580 fed at 1 MB/s, 4,557 at 0.5 MB/s). By default Suricata reads the file, a compressed one from an inflated copy, and the hash still comes from the run's read (`--suricata` alone 2.42 -> 2.00). tshark's `--decrypt` listing is pace-independent (identical output from a file and from a FIFO fed at 0.5 MB/s) and keeps its copy. A system without FIFOs has Suricata read the file; a feed Suricata stops reading for longer than its scan timeout falls back to that too. Its scan timeout now counts from when Suricata has the whole capture: the time it spends waiting on a slow pass is not a stuck scan.
- **`--decrypt` reads the capture twice, not once per stream.** tshark followed each TLS/SSH stream in a run of its own, a read of the whole capture per stream: wannacry-20170516 with its 50 TLS streams 56.07 file sizes per run, NM_2015-08-23 7.53. It now follows them all in one run (200 streams per run at most), splitting the output into the text a run of its own prints for each -- the files are byte-identical -- and lists the streams from a copy of the run's read through a FIFO, as Suricata does: 2.00 for both (`--decrypt --http --dns`: 54.03 -> 2.00, 6.50 -> 2.00). The follow run stops at the last frame its streams need (`tshark -c`, from the listing's frame numbers): streams that end early do not cost a read to the end of the capture. With both `--tls-keylog` and `--ssh-keylog`, one run follows the streams of both. On a capture of loopback HTTPS recorded with its key log (8 TLS sessions, 6 with decrypted application data), the decrypted files are byte-identical to before; `--http --decrypt` 20.67 -> 2.02 file sizes, 21.67 -> 2.02 with an SSH key log too. A run that times out falls back to following its streams one by one; `PCAPPER_TSHARK_FEED=0` has tshark list the file itself. Without FIFOs (Windows) the listing is fed down tshark's standard input (`-r -`); a stalled reader there is caught by a watchdog, as `select()` cannot watch a pipe.
- `--timeline` dates the file transfers it lists from each record's time, kept for its first `PCAPPER_TIMELINE_TIMES_MAX` records (16M, 8 bytes each); later ones come from a scan of the record times.

### `--jobs`

- **In memory too.** A capture held in memory is analysed by forked workers as well: each starts once the analyses it needs are done and reads the packets -- and those results -- from the memory it shares with the main process, with no read and no copy of the packets; the analyses the longest chains wait for start first. `--overview` of NM_2015-08-23: 33.7 s in one process, 19.5 s with 4, 14.3 s with 8 (16 and 32 gain nothing: its longest chain of dependent analyses is ~7.7 s); of asprox_24hr (202k packets): 280 s -> 151 s, of which 38 s is the load, with 7.3 GiB at peak across the nine processes against 1.8 GiB.
- **From disk, the dependent analyses no longer wait for the workers.** They run in the main process at the same time, their own packet loops first, and take each worker's result as it arrives: `--overview` 55.8 s in one process, 33.9 s with 8 workers before, 23.3 s now; `--threats` 40.5 s -> 20.5 s.
- **From disk, workers read no file.** Each read the whole capture (N workers, N + 1 reads); now the main process's own read copies every byte it reads into a pipe per worker, which parses the capture from there -- through a buffer of up to `PCAPPER_TEE_BUFFER_BYTES` (64 MiB) per worker, so one slow worker does not hold the others up -- and checks it got the whole file before any result counts. A head the decode-as check kept is replayed by each worker from the memory it inherits, and copied only from where it stops; a small capture kept whole is not copied at all. asprox_24hr (202k packets) `--threats` from disk: 464 s in one process, 229 s with 4 workers, the capture read once (1.01 file sizes, the workers included). Analyses that report the capture's hashes stay in the main process, whose read computes them.
- **Automatic count.** One process per usable CPU (the process's CPU affinity, not the machine's count), at most 8, when the run is worth it -- packets x analyses 500,000+, where it was "200,000+ packets, from disk" -- and never more than the plan has analyses. In memory no more than half the available memory allows at ~6 KB per packet per worker (a worker that walks the packets copies their pages). From disk only as many workers as keep pace with the main process (3 for `--overview`: 2 and 8 finish at the same time), the packet count taken from the capture's head the run reads first (kept and replayed), not a sampling read. Workers are balanced by analysis cost instead of round-robin. A run with VirusTotal or geolocation lookups stays in one process unless `--jobs` says otherwise: concurrent lookups could meet a rate limit one process does not.
- Reports are byte-identical with and without `--jobs`, in memory and from disk.

### Top and bottom 10

- **Rankings show the top 10 and the bottom 10 by default** -- the rarest, where the long tail of an investigation lives -- with a line saying how many sit between them (`┄ 37 more domains · bottom 10 below (-v shows all)`); `-v` shows every row. This covers DNS domains, HTTP hosts / URLs / user agents / clients / session tokens, TLS server names / fingerprints (one ranking across JA3, JA4 and JA4S) / clients / destinations, strings URLs / e-mails / domains / strings, TCP/UDP conversations / destination ports / files, the IP intelligence hosts, protocol conversations, the summary's protocols, the overview's hosts / protocols / services, ICMP payloads, host details' services reached and remote access, every value/count table (commands, queries, SPNs, OIDs, operations, cookies ...), OT devices / artifacts / commands / CIP services / PCCC commands / tags written, LDAP searches, Modbus exceptions and SSH outcomes. Tables in time, severity or score order are unchanged.
- Separate "top" and "rarest" sections became one ranking: DNS "Top domains" + "Rarest names" are "Domains" (base domains; -v keeps every name), HTTP "URLs" + "Rare URLs" are "URLs", strings "Top strings" + "Rare strings" are "Strings".
- Analyzers that cut a ranking now keep its true bottom and its size: the overview's hosts, protocols and services (top 24 plus the bottom 10), ICMP payloads (top 190 plus the bottom 10) and the strings rankings. When the middle was not kept the line says so: `(-v shows 14 of them)` by default, `466 more hosts not kept` with -v.

### `--dnsqueries`

- **New: every DNS lookup with the response observed for it** -- client, server, name, type and what came back (the answers with their CNAME chain, NXDOMAIN or another error, `no response`, or `(query not captured)` for a response whose query predates the capture). LLMNR and mDNS lookups are included and labelled; an LLMNR query is paired with whichever host answered it. Each distinct lookup is listed once at its first sighting with ×N; `-v` lists every query with its packet number, transaction ID and round-trip time. It is a step like any other: `-ip` (that host's lookups), `-summarize` (each row names its capture), `-vt` (a VirusTotal column), BPF/time filters and the JSON/CSV/SQLite exports.
- **`--timeline` and `--hostdetails` no longer list DNS lookups**: a line says how many there were and that `--dnsqueries -ip <host>` lists them. A lookup VirusTotal flags stays on the timeline -- resolving a bad domain is an event.

### Fixed while redesigning

Reading every report against real captures turned up analyzer bugs; each fix is pinned by a test.

- **`--scan` called DNS servers scanners**: a resolver's replies from UDP/53 to a client's random source ports were counted as a UDP port scan (Smoke Loader's gateway was a HIGH "internal scanner"). Datagrams from a service port to an ephemeral port are now replies, not probes.
- **`--scan` rated nmap's default top-1000 sweep CRITICAL "ICS reconnaissance (T0846)"** because that list contains 2222, 4000 and 20000. OT reconnaissance now needs a narrow or OT-heavy port set or an OT port that answered open; a broad sweep says it included OT ports and was not OT-specific. The same sweep was guessed "Masscan/ZMap-like"; it is now "Nmap (default top-1000 port scan)", a 60k-port scan a full port range, and only internet-scale horizontal sweeps Masscan/ZMap-like.
- **OT protocols reported from a coincidental port**: a Modbus slave on 502 answering a master whose source port was 3671, 4000 or 4059 was counted as KNXnet/IP, ROC Plus or DLMS/COSEM. A packet from another well-known or OT service port is that service's reply. `--overview` also listed those families (and POWERLINK with 0 packets); a family is now listed only when its deep dive finds the protocol.
- **HTTP and TLS servers labelled OpenVPN**: any mid-stream binary segment (an EXE download, TLS application data) could parse as an OpenVPN-over-TCP control frame and relabel the whole service, e.g. the Smoke Loader payload server on port 80. Only a direction's first payload, opening with a HARD_RESET, identifies OpenVPN now.
- **"OT risk score 5/100: High-severity IT detections"** on captures with no OT traffic at all: IT detections now add to OT risk only where there is OT activity.
- **`--mitre` scored enterprise Impact (T1498 network DoS) as "OT process/safety impact"**; only ICS-framework hits count.
- **DNP3 errors on IT traffic**: any TCP payload containing `05 64` was tracked as DNP3, and a sequence gap in it reported "DNP3 TCP sequence gap" (shown by `--dnp3`, `--mitre` and `--threats` on WannaCry). Stream notes are now reported only when DNP3 was decoded.
- **Certificate expiry was judged against today** instead of the capture time, so every old capture's certificates were "expired"; `--certificates` and `--tls` now use the time the certificate was presented.
- **`--ldap`** decodes cleartext LDAP with a BER parser: simple-bind credentials, search bases/scopes/filters, writes to security-sensitive attributes and real operation counts (the old substring scan counted "Delete"/"Modify" inside DNs). SASL/GSS-SPNEGO binds are no longer reported as anonymous.
- **`--ntlm` dropped two-character domains**, which made the NetNTLMv2 hashes uncrackable; hashes now use the user and domain as sent.
- **`--syslog`** parses RFC 5424/3164 messages without a HOSTNAME or with a TAG, lists the messages, and no longer raises "Malware indicator" on binary payloads on port 514.
- **`--ctf` missed base64/hex flags in query strings and forms**: a `key=value` token is now decoded value-first (`?d=<base64 flag>` was never found).
- Device fingerprints took words as versions (Telnet "version=of"); version/firmware values must contain a digit. Filenames are no longer read out of directory listings or across sentence spaces.
- `--compromised` explains executable payload downloads (they used to get the generic "flagged by the analyzer" reason); the files deep dive in `--overview` no longer reports "Files extracted via dpkt" as a highlight.

### Fixed after the redesign

The gaps the redesign left open, and the analyzer problems found while closing them; each is pinned by a test.

- **Host names behind CNAMEs.** The host-name analysis read DNS responses the way scapy laid them out before 2.6 -- one record carrying the next -- while scapy 2.6 keeps each section's records in a list: only the first record of a section was read (and every DNS packet raised a DeprecationWarning). An A/AAAA record behind a CNAME never mapped its name to the address; `--hostnames` now finds +2 to +230 mappings on four of five captures checked (none lost), and `--ips`, `--hostdetails` and `--overview` show them.
- **DCSync on a dynamic port went unreported by `--domain`**, and by `--rpc` whenever the capture started after the bind. `--rpc` names every DRSUAPI operation, reads alter-context PDUs, and recognises a bind-less DCSync from its opnum sequence (DRSBind, then DRSGetNCChanges among DRSCrackNames / DRSDomainControllerInfo / DRSUnbind — opnums travel in clear text even when the stubs are sealed). A DRSGetNCChanges call is now its own HIGH finding (T1003.006) in `--rpc`, and `--domain` raises "DCSync from a non-DC host" from those sessions on any port (replication between known DCs is noted as benign).
- **IS-IS was invisible to `--routing`**: IEEE 802.3/LLC frames (scapy's `Dot3`) were skipped before the IS-IS check. The decoder also used the wrong PDU-type table and header offsets (Hellos were listed as LSPs) and read TLV 9 (LSP Entries) as authentication, reporting CSNP contents as "plaintext authentication". PDU types, per-type headers and TLVs now follow ISO 10589; only TLV 10 is authentication, and only its cleartext type is reported as a plaintext password. `-v` lists each routing artifact once with how often it was seen (a two-router capture repeated the same system ID 31 times).
- **`--vnc` counted only the RFB banner packets** (2 of 1,619 in an UltraVNC infection capture) and called a reverse connection's server banner the client's. A VNC flow is now tracked from its handshake on any port, the side that speaks first is the VNC server, and a server that dialled a listening viewer is a "Reverse VNC" finding (HIGH to an external viewer, T1219) with the UltraVNC repeater ID, the strings in its hello buffer and how far the handshake got.
- **`--modicon` reported all Modbus/TCP as Modicon** and doubled every Modbus write alert. It now covers Schneider's UMAS (Modbus function 0x5A) only; the UMAS table gained the missing functions (KEEP_ALIVE 0x12, DATA_DICTIONARY 0x26, the 0x30–0x35 project transfers, READ_ETH_MASTER_DATA, GET_STATUS_MODULE) and a program read off the PLC is a HIGH "Program Upload" (T0845) finding.
- **Modbus replies read as other OT protocols** when the master's ephemeral port equalled an OT port: 2221/2222 became EtherNet/IP and CIP "Reset/Create" commands, 20000 DNP3, 3671/4000/4059 KNX/ROC Plus/DLMS. A packet from another well-known or OT service port is now that service's reply in every OT analyzer.
- **`--ot-commands` counted each Modbus write twice** (the device echoes it) and listed device-to-master "command sessions"; Modbus commands are now counted from requests.
- **`--modicon` help and `docs/reference.md`**: the help now says it covers UMAS, and the reference listed `--codesys` as `--odesys`.
- **`--kerberos` and `--domain` headlines counted the whole capture** as Kerberos / domain packets; they now count Kerberos and the domain services, and a capture without Kerberos says so.
- **`--correlate` and `--baseline-save`/`--baseline-compare` had no host inventory**, so only services were correlated or compared. The host analysis now runs for them; multicast and broadcast addresses are not hosts, and broadcast/multicast MACs (an ARP request's destination) are no longer attributed to hosts. A port whose service banner changed (a CDN edge tag) is reported as that port changing (`80/tcp HTTP ECS (ord/4CD5) -> HTTP ECS (dca/249B)`), not as one port closing and another opening.
- **Internet addresses were given the gateway's MAC** in `--hostdetails`, host inventories and baselines: every frame to an off-link address carries the router's MAC, so 8.8.8.8 "had" the lab gateway's VMware MAC, a baseline reported it changing with the gateway, and two gateways made every public address an identity collision. A MAC that frames pair with two or more public IPv4 addresses is a gateway's, and is no longer attributed to a public address unless ARP or DHCP binds them; private addresses (the router's own LAN address) keep it.
- **ARP probes made `0.0.0.0` a HIGH "ARP IP/MAC Conflict"** (and a suspected victim in `--compromised`): RFC 5227 probes are sent from 0.0.0.0 before the sender owns an address, so two devices probing looked like one address claimed by two MACs. Probe senders no longer count as address claims.
- **PowerShell remoting read as obfuscation and a covert channel** (`--obfuscation`, `--compromised`): WinRM on 5985 seals every SOAP message (`multipart/encrypted`, HTTP-SPNEGO/Kerberos/CredSSP session encryption) and authenticates with NTLM / Kerberos tokens in base64, which were "high-entropy payloads on a non-encrypted port" and "binary base64 blobs". A declared encrypted body is expected high entropy, and an `Authorization` / `WWW-Authenticate` Negotiate, NTLM or Kerberos token is authentication (unless it decodes to an IOC).
- **CIP findings were listed twice in `--threats` / `--compromised` / `--overview`**, once from the CIP analyzer and once from EtherNet/IP, which decodes the CIP it carries: a PLC Stop or an enumeration run counted as two issues, worded and counted slightly differently so the exact-duplicate collapse missed them. For the same title and severity the CIP analyzer's finding is kept.
- **A DHCP client identifier was a HIGH "Potential DHCP Option Exfiltration"**: option 61 holds a MAC or DUID, binary by design, so its entropy always crossed the threshold, and a client resending it in each DISCOVER/REQUEST reached the three-message trigger. A client identifier now counts only when oversized, and the finding needs three distinct suspicious values from the client.
- **The test suite wrote `carved/` into the checkout** (`test_determinism` ran `--carve` from the repo root); it now carves into a temporary directory.
- **LLMNR was invisible to `--dns`, `--hostnames` (and the new `--dnsqueries`)**: scapy decodes UDP 5355 as `LLMNRQuery` / `LLMNRResponse`, which are not `DNS` subclasses, and `getlayer(DNS)` matches the exact class. The DNS report's LLMNR counters, its LLMNR client/responder lines and its "LLMNR traffic observed" finding never fired (wannacry-20170516: 26 LLMNR packets from the infected host, now reported); hostnames from LLMNR answers were never collected.
- **The strings report's "domains" were the last label of each name** (`adobe.` for www.adobe.com: the pattern's capturing group made `findall()` return the group) **and HTML/JavaScript tokens** (`element.value`, `n.push`, `window.Document`). Whole names are counted now, only when they end in a known top-level domain written in one case.
- **The overview's host count was capped at 24** ("24 hosts (… internal)" for any larger capture): it counted the hosts its table kept. It counts every host now.
- With colour on, an encoded PowerShell command's decoded script could be printed under the "… more rows" line, decoded from a row that was not shown; decoded scripts now follow their own rows in both halves of a ranked table.
- **Findings with traffic both ways were labelled as a host talking to itself** (`10.10.110.133 -> 10.10.110.133`): the flow came from the top source and the top destination separately, and with two-way evidence the same host tops both. The flow now runs to the first destination that is not the source.
- **`-summarize` sent 37 analyzers to the generic rollup** (DNS, HTTP, TLS, Kerberos, LDAP, CTF, the OT protocols …) because their frozen summaries could not be merged. They now merge into their own report, per-capture records keep their capture's name (CTF flags show it), counts add while link types, versions, ratios, rates, scores and unique counts do not, durations are the span the captures cover (the CTF rollup summed them), capture metadata is listed per file, and rollups read "all captures (N)" / "in these captures".

### Large captures

A capture too large to keep in memory used to be read, and every packet dissected by scapy (~150 µs each), once per analyzer: `--threats` made 96 full passes, `--ot-commands` 41, `--overview` 25. On the 12 GB, 54M-packet TU Wien smart-factory capture that was hours for `--modbus` and days for the fan-out flags. Every change below gives the same report as before (verified byte for byte against 2.9.0 on 140 OT captures × 48 OT flags and 60 mixed captures × `--threats`/`--overview`/`--ot-commands`, from disk and from memory).

- **Lightweight packets.** Analyzers that only need ports, endpoints and the TCP/UDP payload (every OT analyzer: the ~40 port/EtherType ones, Modbus, DNP3, CIP, ENIP, GOOSE/R-GOOSE, SV, PTP, LLDP/DCP, IEC 101/103, synchrophasor, safety/TriStation and OPC Classic; the `--files` stream pass; auto-decode) read records straight from the capture bytes, about 2–4 µs per packet, and only dissect a packet with scapy when something needs scapy's view. Which layer scapy would build is asked of scapy's own binding tables, so a bound application layer (TLS on 443, DNS on 53 ...), a tunnel, IP options, IPv6 extension headers, ICMP errors or an 802.3 frame get scapy's answer. Checked packet by packet against scapy on 1.6M packets from 899 captures in every format pcapper reads (pcapng, nanosecond, modified pcap, gzip, cooked, raw IP, 802.11, loopback).
- **Prefiltered reads.** Port analyzers and Modbus drop the packets they can never claim before any parsing; their packet/byte totals and time span still cover every packet. POWERLINK (EtherType, UDP 3819, v1) and PROFINET (PNIO-CM ports, RT EtherType) analyse their encodings in one read instead of three and two.
- **BSD-loopback captures** (linktype 0 and OpenBSD's 108) take the lightweight path too; the address family is decoded by scapy's own field, so it agrees with scapy byte for byte (checked on 17,246 loopback packets from 260 captures).
- **Shared reads.** `--threats`, `--overview`, `--ot-commands`, `--mitre`, `--compromised`, `--timeline`, `--hostdetails`, `--files`, `--ctf` and multi-flag runs on a capture read from disk run their analyzers concurrently over one read of the capture (see Read once), instead of one read each: `--threats` from disk 359 s → 47 s on a 20k-packet slice. The analyzers share each dissected packet. Some scapy layers change themselves while being built back into bytes (TLS/SSLv2 records; FCS, ICMP-extension and DCE/RPC trailers), so two analyzers building such a layer of the same packet take turns; all other builds run without waiting. Each TLS record is rebuilt into bytes once and reused by the ~30 analyzers that read it, instead of once per analyzer.
- **`--jobs N`** runs those analyses in N processes. Every analysis still sees the whole capture, so the report is identical to `--jobs 1`; 48 OT flags on a 200k-packet slice 104 s → 53 s with `--jobs 8`. The count is chosen automatically (see `--jobs` above; `--jobs 1` keeps one process).
- **`--split N`** analyses N contiguous windows of a capture in parallel and reports each window on its own: what `editcap -c` plus a pcapper run per part gives. Merging per-window detections into one report was tried and rejected: counts merged exactly, but unit IDs, register ranges and distinct-host counts were added across windows.
- **Large-capture notice.** Above ~1M packets (estimated from samples through the file) pcapper says how many packets the capture holds, how long one full read takes on this machine (timed on its first packets), whether it stays in memory, and what makes it faster (with `-v`; see Progress display).
- **Memory budget by packets, not file size.** A dissected packet takes ~6 KB, so a 256 MB capture of small frames needed ~20 GB once loaded. A capture is now kept in memory only when its estimated packets fit `PCAPPER_CACHE_MAX_PACKETS` (default: a quarter of available memory, 100k–4M packets).
- In memory, per-packet transport records and endpoints are kept on the packet and shared by every analyzer: `--threats` 35.4 → 31.6 s, `--overview` 39.5 → 36.0 s on a 20k-packet slice.

### Capture input

- **Gzip-compressed captures** (`.pcap.gz`, `.pcapng.gz`) were refused as "not a pcap/pcapng capture" (and skipped in directory scans). They are now read decompressed, and their report matches the one for the decompressed capture except for the file's own name, size and hashes (the capture summary says `pcap (gzip)`). A compressed capture cannot be split into `--split` windows; its packet count is estimated from its start, scaled by the compression ratio there.

### Fixed

- **`--overview` of a capture read from disk failed most deep dives** (`AttributeError: 'dict' object has no attribute 'file_type'`): a loop variable shadowed the capture metadata the deep-dive closures pass on. Large captures (not kept in memory) always took this path.

Each alert now lists its five earliest by event time, and the multi-host fan-out check breaks ties by signature (ranked lists already broke ties by name).

### `--files` (WannaCry capture)

#### Added

- **`--files` checks `known_malware_filename` and `internal_executable_staging`**, both scored by the verdict. The first fires (high) on a transferred file named after an unambiguous malware family or offensive tool (`wannacry`, `wcry`, `mimikatz`, `rubeus`, …; dual-use admin tools are excluded). ## 2.5.0 — 2026-09-14

Third pass of the 2026-09 production-readiness review: the roll-ups, the beacon detector and the compromise assessment. Every item below is a report that was wrong rather than failing, pinned by a test on a synthetic capture; the suite grew from 572 to 584 tests.

### Fixed

- **Reconnecting beacons were never scored (`beacon.py`).** The flow key dropped the client port before the per-connection key was built, so every connection between the same two hosts on the same service shared one key: an HTTP C2 that opens a fresh connection per check-in (Ursnif, Cobalt Strike HTTP) collapsed into a single event and never reached the scorer. Since 2.0.0 the TCP beacon path only ever saw persistent connections. With reconnects live again, the burst-then-sleep profile also needs a moderately stable candidate, so forty browser connections to one CDN with random gaps are not a WARNING beacon.
- **An HMI polling its PLCs was the most likely compromised host (`compromised.py`, `mitre.py`).** Three defects stacked: the beacon step read the service port from `dst_port`, which is `None` for every TCP candidate, so the OT-baseline branch never fired and each Modbus poll was a HIGH beacon; info-level entries weighed 1 each, so five of them alone crossed the listing threshold (five polled PLCs, or five API tokens in transit); and the threat engine's own "baseline cyclic polling" downgrade came back as warning evidence. Baseline periodicity now carries a machine-readable `internal_periodicity` field, is context (info) in the compromise assessment, forms no incident cluster, and is left unmapped by `--mitre` instead of becoming a Command and Control technique credited as an objective-stage tactic. The stage classifier matches at word starts, so "Unauthorized command" is no longer a credential stage and an `ec2-…amazonaws.com` peer is not C2.
- **Numbers in a detection's own prose were domain IOCs (`compromised.py`)**: `score 0.98`, `interval 90.00s` and `duration 58.50m` matched the domain pattern, were listed as the host's IOCs and, being identical for every host with a similar cadence, grouped unrelated hosts into phantom campaigns. A domain IOC now needs an alphabetic TLD. The compromise roll-up also rebuilt each host without its announced roles and crown-jewel flag, and three more sorts (technique heat, host priority, incidents, campaigns) carry a total order.
- **`-summarize` roll-ups dropped whole sections.** A systematic check — run each analyzer on two fixtures, merge, and list every dataclass field that is empty in the merge while populated in an input — found the `--hostdetails` roll-up silently missing all eight dossier sections added in 2.1.0 (announced NetBIOS identity, authentication events, TLS fingerprints, SMB share access, mail activity, peer intel), the `--dhcp` roll-up missing its lease table, per-MAC hostnames, option statistics and OS fingerprints, the `--cip` roll-up missing both size histograms, and the timeline roll-up losing its bin count when one capture had no OT traffic. Five roll-ups (`--ips`, `--rpc`, `--email`, `--snmp`, `--overview`) reported the *sum* of per-capture durations while every section around them reported the window, so one report showed two different durations for the same inputs. `tests/test_merge_summaries.py` now runs that check over every merge function.
- **A truncated HTTP download was recorded as a complete file with a confident hash (`files.py`).** A response whose stream ended before its declared `Content-Length` — the capture stopped, packets dropped, snaplen — produced an artifact indistinguishable from a whole one. The note now reads `HTTP Response Body (TRUNCATED: 1552 of 5000 declared bytes)`; chunked and gzip bodies were verified to decode to the right bytes and hashes.
- **Sizes under about 5 KB printed as `0.00 MB`** in 230 places (artifact tables, conversation volumes, capture totals): a 1.5 KB PDF or a 900-byte credential file had no visible size. The shared formatter now carries its own unit below a megabyte (`1.52 KB`, `900 B`); output at and above 1 MB is unchanged.
- **The analysis memo keyed a forced packet view on `id(list)`**, which CPython reuses once the previous view is freed, so two consecutive filtered views of the same capture with the same length could alias. Views now carry a registration serial.
- **A beacon heartbeating over one persistent connection was invisible (`beacon.py`).** The detector scored connection start times only, so a reverse shell, a websocket C2 or a Meterpreter keep-alive that holds one socket open and sends a request every minute never became a candidate. When a session has too few connections to score but its connections carry enough client requests, the request times are the event stream (`basis=requests-in-one-connection` in the evidence), held to the same cadence bar as datagrams so an SSH session's keystrokes or a keep-alive HTTP session's irregular requests do not qualify on count alone. The per-connection tables are also capped (`PCAPPER_MAX_BEACON_CONNECTIONS`, default 250,000) and the report says when the cap was hit.

## 2.4.0 — 2026-09-14

The 2026-09 production-readiness review, continued across every analyzer. The pattern that recurs below is a report that was *wrong rather than failing*: a server counted as its own busiest client, a window that spanned the whole capture, a padded frame read as protocol bytes, a heuristic that fired on healthy traffic. Each fix is pinned by a regression test built on a synthetic capture; the suite grew from 255 to 572 tests.

### Fixed — client/server roles

Every packet's *sender* used to be the "client" and its *receiver* the "server". A reply from a service therefore made the server a client and the client a server, so on any capture with normal request/response traffic the top-clients table listed the directory server, the KDC or the resolver, and the top-ports table listed the clients' ephemeral ports. Roles now come from which end holds the service port, and a service port on the *source* side only identifies the service when the destination is an ephemeral port — a flow from ephemeral 389 to 443 is not LDAP. Analyzers corrected: **UDP, TCP** (roles from the handshake, port heuristic otherwise), **SNMP, LDAP, Kerberos, NTLM** (the carrier service was read from the packet's dport, so the server's Type-2 challenge counted no service), **QUIC** (flows were also split in two and one half named after the client's ephemeral port), **DNS-over-TLS/QUIC, HTTP/2** (only segments containing the literal preface were counted, so the server side of an h2c connection never appeared and every binary frame after the preface was invisible; connections are now tracked from the preface or an `Upgrade: h2c` exchange, and TLS sessions offering ALPN `h2` are reported), **WinRM, RDP, WMI, PowerShell, Telnet, VNC, TeamViewer, VPN, AIM, syslog, BGP, Modbus, DNP3, safety-system ports, IEC 60870-5-101/103** (the FT1.2 PRM bit says which end is the primary station), **OPC Classic** (bind_ack/response PDUs come from the server; the interface UUID appears in both directions).

### Fixed — false positives on healthy traffic

- **Kerberos AS-REP roasting (`kerberos.py`)** was inferred from "five AS-REPs and no `KDC_ERR_PREAUTH_REQUIRED`", which every healthy domain logon satisfies. The evidence is an AS-REP that answers an AS-REQ carrying no pre-authentication data (`PA-ENC-TIMESTAMP`, PKINIT or FAST; `PA-PAC-REQUEST` is in every Windows AS-REQ and must not count). The finding now names the roastable accounts and the requesting clients, with a `hashcat -m 18200` pointer. Principal names and realms are now read from the ASN.1 (`PrincipalName` components are separate `GeneralString`s, never the `HTTP/host` text the regexes expected, so the SPN and cname regexes only ever matched captures of tool output).
- **FTP (`ftp.py`)**: any `NNN text` line or `USER`/`PASS`/`QUIT` on any port was parsed as FTP, so every SMTP and POP3 session appeared in the FTP report with its banner and its credentials. A flow off the FTP control ports is now held back until an FTP-specific command or reply code confirms it, and the parked lines are replayed on confirmation so nothing is lost.
- **Brute force (`threats.py`)** was twenty connection attempts regardless of time: twenty SMB sessions from a workstation to its file server over an eight-hour day. The attempts must now average at least one per thirty seconds. **UDP flood** was a total (5000 datagrams) rather than a rate; a resolver or syslog collector receives that in an hour. It is now 500 packets per second sustained over a capture of at least one second.
- **Domain exposure (`domain.py`)** flagged a query to 8.8.8.8 as a "public domain-service endpoint" because DNS is in the domain port set; the HIGH finding fired on nearly every enterprise capture. Only Kerberos/LDAP/SMB/RPC reaching a public address is an exposure, and the finding names the services.
- **syslog (`syslog.py`)**: any TCP segment whose first bytes contained `<` was a syslog message, so HTML and XML responses on 80/443 filled the syslog report. Off the syslog ports the message must open with a PRI (`<13>`).
- **DNS over HTTPS (`encrypted_dns.py`)**: `b"/resolve" in payload` matched `/resolver`, `/resolve-ticket` and any body mentioning the word. Only the request line is consulted now (RFC 8484 `/dns-query`, Google's `/resolve?name=`, or an `application/dns-message` content type).
- **Hostname inventory (`hostname.py`)**: a workstation registering the `CORP<1C>`/`<1E>` group names got `corp` recorded as its hostname (the NetBIOS suffix and the group bit were discarded); an SSDP `NOTIFY` had its device name pinned to 239.255.255.250 instead of the sender; and URL hosts that are bare IP addresses were recorded as hostnames of themselves.
- **Malware roll-up (`malware.py`)**: merging several captures produced a verdict with no score at all; the roll-up now carries the worst single capture's score and wording (summing would let many weak captures add up to "MALWARE PRESENT") with its reasons and evidence lists.
- **PTP (`ptp.py`)**: every message type was credited to the first MAC ever seen, so the per-source Management finding named the wrong device.
- **Retransmissions (`health.py`, `tcp.py`, `analyzer.py`)**: pure ACKs, keep-alives and window probes legitimately repeat a sequence number and were counted as retransmissions; only a data-bearing segment can be one. In `health.py` the segment length also came from `bytes(tcp.payload)`, which on a padded minimum frame is six pad bytes, so every padded pure ACK looked like a repeated 6-byte data segment.
- **Scan detection (`scan.py`)**: a bare RST (the scanner tearing a half-open connection) counted as a closed-port response; stealth scans (FIN/NULL/XMAS/Maimon/ACK) and UDP scans were silently ignored; ICMP unreachables were attributed to the wrong host. **IP scan breadth (`ips.py`)** counted broadcast, multicast and link-local destinations as targets, so service discovery read as a sweep.
- **DHCP (`dhcp.py`)**: an OFFER answering a DISCOVER was reported as a transaction-integrity violation because only REQUEST transaction ids were remembered.
- **Certificates (`certificates.py`)**: the DNS-SAN mismatch check compared the *client* IP with the certificate's DNS names and so flagged every certificate; only an IP SAN can be checked against the wire. Endpoint profiles are now per presenting server, `tls_packets` counts records on any port, and `--tls` and `--certs` share one memoized result.
- **Skeptical filter (`skeptical.py`)**: the "blocked outbound tunnel" downgrade applied `all()` to an empty list of SNI ratios, so any TLS handshake-failure finding that merely mentioned "proxy" was downgraded; CDN membership was a string-prefix test (`23.11.` cannot say whether 23.11.x is in a /16 or a /13) and is now a CIDR set; invalid addresses such as 999.1.1.1 were accepted.
- **Device detection (`device_detection.py`)**: "Boarding" became software "Boa rding"; Cisco IOS was reported as Apple iOS; the two-letter fragment "ge" became General Electric; Google Drive became a motor drive.
- **NetBIOS/SMB (`smb.py`)**: the SMB2 NEGOTIATE ServerGuid and capabilities were read mid-GUID; CREATE request names were read from body offsets 48/50 instead of 44/46, so real CREATE requests never yielded a name; the FileId was read from 64 instead of 56.
- **ARP trailer (`arp.py`)**: the bytes after the ARP body are `Padding` to scapy, never `Raw`, so the plaintext/filename extraction never found anything.
- **Analyzer windows**: `first_seen`/`last_seen`/`duration` in a protocol view spanned every packet of the capture, so a one-minute Kerberos exchange in an eight-hour capture reported an eight-hour window and every per-second rate derived from it was wrong. They now span the protocol's own packets in TLS, NTP, SNMP, UDP, TCP, mail, LDAP, NTLM, Kerberos, QUIC, encrypted DNS, HTTP/2, VPN, SSDP, NetBIOS, GOOSE, SV, LLDP/DCP, PTP, OPC Classic, IEC 101/103, C37.118, AIM, WLAN and routing.
- **Ethernet padding**: scapy hangs the pad of a 60-byte minimum frame under the transport layer, so `bytes(tcp.payload)` of a data-less segment is up to six NULs. Character-mode Telnet (one keystroke per segment, always padded) carried five NULs per key into the transcript; a pure ACK to a PLC port counted as an "OT command out" in the remote-access pivot check; refused connections looked data-bearing to the beacon scorer; and the file carver spliced pad bytes into the stream. All read the segment length from the IP/TCP headers now (`utils.tcp_segment_length`), as the OT analyzers already did.
- **Determinism**: sorts on packet count alone (`ldap`, `kerberos`, `rpc` conversations), a hit set iterated in hash order (`creds.py`), a set difference rendered in iteration order (`baseline.py`), a crown-jewel asset picked from a set (`threats.py`) and the verdict-summary row order all changed output from run to run under hash randomisation. Each now carries a total order.
- **DNS questions**: `qd` is a list of `DNSQR` in scapy 2.6; six modules read `dns_layer.qd.qname`, which the deprecation shim proxies to the first entry with a warning per packet. A shared `utils.dns_questions()` returns every question and is used throughout.
- **Packet sizes (`sizes.py`)** used the captured length, so a snaplen capture reported every packet as at most snaplen bytes; sizes are now on-wire lengths. The top bucket ended at 65535, so GRO/TSO "packets" above that vanished from the table.
- **Smaller ones**: `pcapmeta` kept only the last interface's drop count instead of the sum; a ragged table row raised `IndexError` and killed the whole report; `PROPFIND` was in the WebDAV misuse detection but the verb was never parsed; the mDNS/LLMNR/DHCPv6 wire-format names were not decoded; the OT-presence gate in the consolidated report dropped every genuine CIP detection because CIP is counted under EtherNet/IP; the report printed two differently-worded OT verdicts; `mitre` keyword "s7" matched inside "s7comm-plus-xyz"; a 33–63-character hex run was treated as a hash.

### Security

- **A config file in the current directory is no longer loaded.** pcapper is run from inside evidence directories, and a `pcapper.toml` there could turn on `vt` (send the investigation's domains and URLs to VirusTotal) or `ip_geo` (send every public IP to ip-api.com) or redirect the output paths, with nothing on the command line to show it. Only `--config`, `PCAPPER_CONFIG`, `~/.pcapper.toml` and `~/.config/pcapper/config.toml` are consulted; the CLI prints `Config: <path>` on stderr, lists unknown keys, prints a notice for any key that enables network egress, and treats a config that exists but cannot be parsed as an error (exit 2) rather than a silent fallback.
- **Nothing internal leaves the box for reputation lookups.** The VirusTotal passes in `dns.py`, `http.py` and `webrequests.py` and the VirusTotal/OTX/AbuseIPDB lookups in `ips.py` sent every observed name, including `fileserver.corp`, `printer.local`, reverse-lookup zones and RFC 1918 addresses — each one a disclosure of the investigated network. Only syntactically valid public hostnames and routable addresses are submitted; the withheld count is reported. Wire-derived names are percent-encoded before entering a URL, so a `/` or `?` in a hostile qname cannot rewrite the request path, and every pass has a wall-clock budget (500 lookups at an 8 s timeout used to be an hour with nothing to show).
- **A file whose name ends in `.pcap` but has no capture magic is rejected (exit 2)** instead of being read as an empty capture and reported as zero packets with no error — the way a gzip-compressed or renamed file used to pass silently.
- **Recovered secrets are owner-only from the moment the file exists** (`utils.open_private`, `safe_write_bytes`): the earlier fix chmod'd after a world-readable write, and the SQLite export file is created before sqlite opens it. **Spreadsheet formula injection** in exported strings is neutralised.
- **`--decode` decompression is bounded** (32 MiB): gzip, zlib, bzip2 and xz all ran unbounded on operator-supplied text.
- **Bounded memory** on large captures: per-key sample lists in the DNS, HTTP, SNMP, beacon and DHCP analyzers, the ARP pending-request table, the DNS pending-query table, the stream-follow total, and the web-request list were unbounded and were the largest allocations on busy captures.

### Changed

- **One packet loop.** Every analyzer used to hand-write the same reader loop — get the reader, `tell()` the stream per packet for the status bar, close both in a `finally`. `pcap_cache.iter_packets()` is that loop as a generator with throttled progress, and all 81 analyzers with a packet loop now use it and accept the shared `packets=`/`meta=` view, so a chained run never re-reads the file.
- **Memoization shares the stored object on a hit** instead of deep-copying it, which was the dominant cost of a hit on the large summaries. Results are treated as immutable: the inner builders that are post-processed in place (`analyze_port_protocol`, `analyze_ethertype_protocol`) are not memoized, `tests/test_review_guards.py` pins in-place mutation of a memoized result at zero, and the old copying behaviour is available with `PCAPPER_ANALYSIS_MEMO_COPY=1`. Twenty-two more modules' analyzers are memoized.
- **`utils` is the one home for the shared primitives** (`env_int`, `open_private`, `safe_write_bytes`, `ip_object`, `is_valid_ip`, `shannon_entropy`, `packet_wirelen`, `tcp_segment_length`, `tcp_flags_text`, `extract_ethertype`, `dns_questions`). The 24 module-local re-implementations found at the start of the review are gone; a ratchet test fails if one comes back.
- **`industrial_helpers.py` makes one packet pass per OT protocol** with a single-pass size histogram, and command endpoints are attributed to the request direction only, so a service is not listed as both `A -> B` and `B -> A`.
- **Per-packet layer walks were cut** in the ICMP, IPs, VLAN and beacon analyzers (up to ten `getlayer` walks per packet), SMB string extraction is a regex rather than a byte loop (about 2 µs per byte before, more than 100 ms for one 64 KB WRITE), `colorize()` no longer makes a syscall per token, and progress goes to stderr so `pcapper ... > report.txt` on a TTY stays clean.
- **VLAN** reports Q-in-Q double-tagged frames as a HIGH finding; **`PcapSummary`** carries `truncated_packets` so byte totals from a snaplen capture are labelled as a lower bound; **`--hosts`** derives passive OS hints from TCP SYN options.

## 2.2.0 — 2026-09-12

### Fixed
- **TCP sequence wraparound no longer mis-orders long streams (`carving.py`, `streams.py`).** Both reassemblers sorted segments by raw 32-bit sequence number. Sequence numbers wrap at `2**32` and initial sequence numbers are randomised across that whole space, so a stream whose ISN sat near the top wrapped partway through the transfer: the post-wrap segments carried low numbers, sorted to the *front*, and the gap rule then discarded or misplaced most of what should have followed. The reassembled buffer was garbled, no file signature was found, and the artifact was **silently not carved** — no error, no warning, nothing in `errors`. Roughly 1 ISN in 43 hits this on a 100 MB stream, which is precisely the large-file-exfil case `--carve` exists for. Both modules now share a single implementation in the new `pcapper/reassembly.py`, which orders by *signed* distance modulo `2**32` — the same comparison TCP itself uses — so ordering is done in stream space and a segment that legitimately precedes the first one observed still sorts correctly. `streams.py` carried the same defect and was not covered by the original report.
- **A carve taken across a gap is no longer published with an authoritative SHA-256.** A missing run of bytes — a dropped packet, a snaplen-truncated capture, a capture that began mid-stream — was closed by plain concatenation. Offsets after the hole no longer corresponded to any position in the conversation, and a signature straddling one produced a blob with a hole spliced out of the middle, hashed and recorded as the artifact. A partially-reconstructed file carrying a confident hash is worse than a reported failure: it is the kind of thing that gets pasted into a report and relied on, and the hash will never match the file it purports to be. Carving now zero-fills gaps, so offsets stay true to the stream and the corruption is visible in the carved bytes; `CarveHit` gained `gap_count` / `gap_bytes`; and any hit spanning a gap is flagged in its note, in the rendered table (new `Missing` column), and in the detection evidence. Stream following records gaps as before without zero-filling, since those bytes become payload previews.
- **`--decrypt` can no longer hang forever on one stream (`decryption.py`).** No tshark call in the decryption path had a timeout, so a malformed or very large capture stalled the whole run with no output and no way to tell a hang from slow progress — on a capture with many TLS streams, across any of a few thousand invocations. All calls now carry a timeout (120 s, override with `PCAPPER_TSHARK_TIMEOUT`); an expiry is recorded in `DecryptSummary.errors` and the next stream is attempted, matching how `threats.py` already handled its own subprocesses.
- **Decrypted IPv6 streams are no longer written under a filename that misidentifies them.** `_stream_label` parsed tshark's `-T fields` output with `.strip().split("\t")`. tshark pads every requested field, so an unmatched one is emitted as an empty column — and for IPv6 the empty `ip.src`/`ip.dst` columns come *first*. Stripping the leading tab before splitting shifted every index down by one, assembling the label as `<srcport>-_to_<dstport>-<ipv6.src>` and sanitising that straight into the output filename. The IPv4 case survived only because its empty columns are trailing.
- **Stream labelling actually works now.** `_stream_label` bounded its per-stream tshark call with `-c 1`, which caps packets *read*, not packets *matched*: tshark read packet #1, applied the display filter and stopped, so every stream except the one containing the capture's first packet fell through to the `stream_<N>` fallback and the feature was effectively inert. Labels are now collected in the single stream-enumeration pass, which also removes the per-stream re-read of the whole capture — `--decrypt` went from 2N+1 tshark invocations to N+1, the dominant cost on a multi-GB capture.
- **`--smb` no longer drops share, account and group names containing a space.** `render_smb_summary` defined `_looks_like_smb_token` and `_smb_preview_tokens` twice, 58 lines apart; Python bound the later copy, whose allowed-character set omitted the space. On a Windows network that filtered out exactly the values an analyst is looking for — `Domain Admins`, `Backup Operators`, `Program Files`, any share or group name with a space in it — and counted them into the `(N filtered)` suffix. The masking effect made it easy to miss: when *every* token contained a space the preview fell back to the unfiltered list, so the drop only appeared once a single space-free token was present alongside them.
- **Fixed a Python 3.12-only f-string in `compromised.py`.** A nested f-string reused the outer quote character (PEP 701), so the module failed to parse on 3.9, 3.10 and 3.11 — every interpreter below the one it was written on, and four of the five the package advertises support for.

### Added
- **A test suite (`tests/`), and CI to run it.** 164 tests over the reassembler, the tshark field parsing, the path-traversal and decompression-bomb guards, the address predicates, the SMB preview regression, output permissions, and golden rendered output for DNS, HTTP, Modbus, protocol summary and carving. Capture fixtures are small, synthetic and committed, generated by `tests/make_fixtures.py`; two of them — `carve_wrap.pcap` and `carve_gap.pcap` — were built to reproduce the two carving defects above and were verified to fail against the pre-fix code. `.github/workflows/ci.yml` runs ruff's pyflakes rules, byte-compiles, imports every module, and runs pytest on Python 3.9 and 3.13, plus a packaging build. The duplicate-helper SMB bug above came out of the same lint run, which is the argument for the CI gate.

### Security
- **A filename taken off the wire no longer reaches the filesystem as a path (`files.py`).** `_safe_output_path` handed the attacker-supplied `FileArtifact.filename` straight to `_unique_output_path`, which calls `Path.exists()` on it. Containment held — the resolve/`relative_to` check did its job, and nothing was ever written outside the output directory — but the probe itself was the problem: on Windows a UNC name such as `\\attacker.example\share\evil.dll` in a capture turned that `exists()` into a live SMB connection to a host the adversary named. That is a multi-second stall per artifact during `-extract`, and an outbound authentication attempt from the analyst's workstation to an attacker-chosen server — the classic UNC credential-coercion shape, reached by nothing more than opening a hostile capture. A new `_local_filename()` now reduces the name to its final component *before* any filesystem access, evaluating both POSIX and Windows separator rules regardless of host OS (so a Windows-style name is neutralised on Linux and vice versa), stripping drive prefixes, NUL bytes and the trailing dots and spaces Windows silently discards, rejecting `.`/`..`/empty, and prefixing the Windows device names (`CON`, `NUL`, `COM1`…, which resolve as devices in *any* directory) with an underscore. The resolve/`relative_to` check is retained behind it as defence in depth. Found while writing the path-traversal tests for this release; the test suite went from 35s to 0.3s once the lookup stopped happening.
- **Recovered secrets and carved artifacts are now written owner-only (`0600`, `0700` for directories).** pcapper deliberately does not redact what it recovers (`reporting._redact_secret` is a documented no-op), so reports, exports, the run log, carved artifacts, extracted files and decrypted streams routinely contain cleartext credentials, LDAP binds, SNMP community strings, session tokens and malware samples. None of those write paths restricted permissions, so under a default umask they landed at `0644` (case and output directories at `0755`) — on a shared analysis host every other local account could read recovered passwords out of another analyst's case directory, and world-readable evidence is harder to defend on chain-of-custody grounds. Tightened at every write path: reports and JSON export (`utils.safe_write_text`), CSV and `_hosts` CSV, the SQLite export (tightened immediately after `sqlite3.connect()`, so the database is never briefly readable while being populated), the `--log-file` run log, case directories, export output directories, carved artifacts, extracted file artifacts, and decrypted TLS/SSH streams. New `utils.restrict_permissions()` / `utils.restrict_dir_permissions()` helpers are best-effort by design: POSIX mode bits are largely a no-op on Windows, and a failure to tighten permissions never aborts an analysis run.

  - **Tag Access Map (process fingerprint)** — symbolic tags aggregated as read vs write with counts and top endpoint, including tags recovered from Multiple-Service-Packet sub-requests (where Logix tag reads actually live). The tag set *is* the process fingerprint.
  - **Asset roles + true-master detection** — masters are now derived from the TCP-level client direction (sent to an ENIP port), so a PLC whose server→client continuation packet is mis-classified by the CIP-direction heuristic no longer shows up as a bogus "master." Multi-master hunt-hypothesis note.
  - **CIP Health** — success vs error responses with rate and top CIP error codes (privilege violation / path errors = failed writes/probing).
  - **Per-server response time (RTT)** — strict per-connection request→response pairing (records only unambiguous depth-1 matches under a LAN-plausible ceiling) so latency is trustworthy rather than corrupted by pipelining.
  - **ForwardOpen connection analysis** — originator→target with O→T / T→O RPIs and originator identity.
  - **Always-on control/program-transfer findings** — a single `Reset`/`Start`/`Stop` (T0816/T0858) or program up/download (T0843/T0845) now raises a HIGH finding; previously only volume thresholds (≥10) fired, missing the stealthy single op.
- Fixed five false-positive classes in `--enip` that flagged benign Rockwell polling (see Fixed).
- **`--modbus` rebuilt as a forensics / threat-hunting / IR triage tool.** Previously a strong statistics dump that went silent on benign captures and left the analyst to derive "is this normal?" by hand. Now, grounded in the Modbus DFIR literature (SANS FOR572/FOR508 network-forensics model, Trustwave "Modbus 101", the FrostyGoop analyses, and Modbus IDS research), it adds:
  - **Always-on Analyst Verdict** — every capture gets an explicit disposition (`CRITICAL` / `HIGH` / `REVIEW` / `BENIGN BASELINE`) plus a one-line baseline (`N masters -> M servers; unit ids; reads/writes/exceptions over Ns`). A clean read-only poll is now stated as a benign baseline instead of producing no verdict at all.
  - **Register / Coil Map (process fingerprint)** — per server+unit, the read vs write address ranges and hottest addresses. The polled/written register set *is* the process fingerprint; a write to a never-read register stands out immediately.
  - **Polling cadence + per-server response time (RTT)** — request-direction poll interval per master→server, and paired request→response RTT percentiles per server (surfaces a laggy/stressed PLC or an abnormal poll rate).
  - **Transaction pairing** — matched req/resp, orphan requests (possible DoS / PLC-down, T0814), unsolicited responses (possible response injection, T0856), and static-transaction-id connections (replay/injection tell). Thresholded + capture-edge-aware to avoid flagging pre-established sessions.
  - **FrostyGoop-style read-then-write correlation** — a write to a register the same actor was just reading (FC3 read + FC6/16 write) is flagged `HIGH` (recon→manipulate, T0836).
  - **Protocol-violation DPI** — malformed MBAP (non-zero protocol id on port 502) and strictly-reserved/undefined function codes (fuzzing / non-compliant client), distinct from legitimate vendor function-code ranges.
  - **New/rogue-master + off-baseline recon** — flags >1 request-issuing master (new-master hunt hypothesis) and elevates Read-Device-ID / Report-Server-ID enumeration from a non-primary source to `MEDIUM` (T0888).
  - **Fuller ATT&CK-for-ICS mapping** (T0831 / T0836 / T0814 / T0856 / T0846 / T0888) and all new baseline structures (`register_map`, `session_cadence`, `rtt_by_server`, `pairing`, `first_seen`) exported to `--json`.
- **Skeptical filter (`pcapper.skeptical`) — default-on downgrading of well-known false-positive shapes** in `--compromised` / `--threats` output. Motivated by a real-world capture that raised 3× HIGH-severity findings that were textbook FP classes: SYN "flood" to Cloudflare/Akamai with 0% SYN-ACK (blocked egress + client retries, not a flood), "periodic HTTP check-in" against `/RockwellSoftware/AssetCentre/AosService.svc` and `/Activplant/VpPlatformService/VpWebService.asmx` (vendor management-platform polling, not C2), and "TLS SNI suppression" against an internal HTTP-CONNECT proxy on port 80 (blocked outbound tunnel, not evasion). Five rules ship in the initial registry:
  - `blocked-egress-syn-flood` — TCP SYN flood where SYN-ACK ratio is at/near zero, or destinations are all CDN prefixes (Cloudflare / Akamai / Fastly / AWS CloudFront / Google / Azure Front Door). Downgrades `high → warning`.
  - `blocked-egress-connection-probe` — "unanswered SYNs" connection-probing heuristic firing across multiple public IPs (not RFC1918). Real probing concentrates on a single target; many public destinations = blocked-egress + client retries. Downgrades `high → warning`.
  - `likely-vendor-polling` — periodic HTTP check-in against a well-known OT/industrial-management vendor endpoint (Rockwell AssetCentre `AosService.svc`, FactoryTalk `pfwAuthz.aspx`, Activplant `VpPlatformService`, AspenTech aspenONE, OSIsoft/AVEVA PI Web API, GE Proficy Historian, Emerson DeltaV, Yokogawa Vnet mgmt, Rockwell Studio 5000 / ThinManager, GE Mark VIe / ControlST). Downgrades `high → info`.
  - `single-host-polling-not-fanout` — HTTP fan-out reconnaissance heuristic where `hosts=1` (many URLs to ONE server = polling, not fan-out).
  - `blocked-outbound-tunnel` — TLS handshake failures / SNI suppression against a destination that also carries HTTP CONNECT or a port-80 proxy shape.
  
  Each downgrade preserves the original severity in `skeptical_original_severity`, attaches a machine-readable `skeptical_rule` id and human-readable `skeptical_reason`, and never silently drops the finding — the renderer surfaces a `[skeptical: <rule>, was <sev>]` marker inline and an indented `Skeptical filter: <reason>` line so the reviewer sees the concrete rationale. Extend by appending a `SkepticalRule` to `pcapper/skeptical.py::_RULES`.

- **`--strict` — disable the skeptical filter.** Raw un-filtered verdicts.

- **Hypothesis lens (`pcapper.hypothesis`) — `--hypothesis <REGEX>`** tags every detection as `relevant` / `adjacent` / `unrelated`:
  - `relevant` — case-insensitive regex match against summary + details + source + evidence + IOCs + ATT&CK technique ids.
  - `adjacent` — no direct match, but the detection carries a technique in a tactic family named by any T-id literal in the hypothesis pattern (built-in tactic-family map covers all enterprise + ICS techniques the detection modules emit).
  - `unrelated` — neither.
  
  Renderer shows `[relevant]` / `[adjacent]` / `[unrelated]` tags next to each finding so the reviewer scans a large compromise output for the ~30% of findings that touch the hunt hypothesis. Example: `--hypothesis 'referrer|host header|SNI|T1071|T1090|credential'` on an HTTP-Referrer hunt correctly tags cleartext-credential leakage as `[adjacent]` (T1552 credential-access family), TLS SNI findings as `[relevant]` (direct match), and unrelated bystander noise as `[unrelated]`.

- **Verdict Candidates block (`pcapper.verdict_summary`)** rendered near the top of `--compromised` output, before the per-finding table. Synthesized accept/reject verdicts:
  - `TP_MALICIOUS_CANDIDATE` — HIGH-severity finding, NOT skeptical-downgraded, source in a known-tradecraft class (`Malware`, `Obfuscation`, `Exfil`, `Beacon`, `Files`). Inspect + confirm before treating as final.
  - `TP_HARDENING` — real security finding orthogonal to any hunt hypothesis but should be in the closure narrative (cleartext credentials, SSLv2 / TLS 1.0 / 1.1, weak ciphers, expired/self-signed certs, SMBv1, PII on the wire).
  - `LIKELY_CONTROL_WORKING` — findings a skeptical rule identified as a *security-control-doing-its-job* signal (blocked egress, blocked outbound tunnel). Not a threat; documents that the control works.
  - `LIKELY_FP` — findings a rule identified as a *well-known false-positive class* (vendor polling, single-host polling).
  - `INCONCLUSIVE` — everything else.
  
  Groups identical findings across many hosts into single rows with `xN` counts. Sorts TP_MALICIOUS_CANDIDATE first.

- **JSON output enriched.** `--json PATH` now includes:
  - Top-level `verdict_summary` per PCAP (structured accept/reject candidates so downstream tooling doesn't parse markdown).
  - Top-level `skeptical_rules` — snapshot of the rule registry so consumers know what each `skeptical_rule` id refers to.
  - Every detection dict carries `skeptical_downgraded`, `skeptical_rule`, `skeptical_reason`, `skeptical_original_severity`, and `hypothesis_relevance`, propagated through the compromise pipeline (previously the compromise module rebuilt the detection dict and silently dropped these annotations).

- **`--verbose` emits per-module start/finish/timing to stderr.** Previously the interactive spinner was the only progress signal — a no-op on non-TTY / background runs, and a 15-minute analysis of 3× 17 MB PCAPs looked indistinguishable from a hung process. Now:
  ```
  [pcapper] Threats <capture.pcap>: starting...
  [pcapper] Threats <capture.pcap>: done in 12.4s
  ```
  Emits `FAILED after Xs (<Exception>: <msg>)` on module errors. Best-effort — never breaks the run.

### Fixed
- **`--enip` raised five false-positive classes on benign Rockwell polling** (all verified against tshark full-reassembly on a real ControlLogix capture):
  - *Non-standard-port* flagged legitimate `:44818` server responses whose client ephemeral port was below the old `32768` threshold (e.g. 3479, 24292). Now gated on both endpoints being non-ENIP ports.
  - *Malformed ENIP Length/CPF* fired on every ENIP PDU that spanned TCP segments (the parser's `length_mismatch = declared > observed` is exactly the segmentation direction). Replaced with a per-pair flood detector that only fires on sustained corruption, not segment boundaries.
  - *Suspicious Invocations ~84%* — `Read_Tag`/`Read_Tag_Fragmented` were lumped into the enumeration/"suspicious" bucket via the shared `ENUMERATION_SERVICE_CODES`. Tag reads are normal polling; the risk overview now tiers High-Risk / Suspicious (config/connection/lifecycle) / Enumeration-Discovery / Normal separately.
  - *CIP Enumeration Campaign* fired on the operational HMI reading device identity across its own PLCs. Now gated on the scanner shape (enumeration across many targets with no operational tag I/O), so a busy operator no longer trips it.
  - *Multiple masters* counted PLCs as masters when a server→client continuation packet was mis-classified as a request. Masters are now derived from the true TCP-level client direction.
- **Compromise-module `_curate_threat_detections` was silently dropping downgraded findings.** Findings the skeptical filter moved from `high → warning` were then discarded by the curation min-signal-score threshold. Curation now preserves any `skeptical_downgraded=True` finding regardless of signal score — the whole point of the annotation is to keep the finding visible AND explain why it isn't the severity the raw analyzer emitted.

- **Compromise-module detection cherry-picker was dropping skeptical + hypothesis annotations.** `analyze_compromised` rebuilt each detection dict from a hand-picked field list, so anything `threats.py::_append_detection_items` had attached upstream (`skeptical_*`, `hypothesis_relevance`) was silently lost by the time the detection reached the compromise renderer / JSON export. All five annotation keys now propagate.
